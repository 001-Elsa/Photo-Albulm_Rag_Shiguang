# 架构设计

## 双模式总览

```text
Personal Mode
  Web UI → FastAPI(personal_api)
        → Query Parser / SearchEngine
        → SQLite + FTS5 + NumPy(+可选 pgvector)
        → 进程内 Indexer(scan/embed/ocr/face/cluster)

Enterprise Mode
  Nginx → FastAPI(enterprise routers)
       → Auth / Ingestion / Search / Jobs / Admin
       → PostgreSQL+pgvector+RLS
       → Redis(session/rate-limit/broker)
       → MinIO(object storage)
       → Celery Worker/Beat(AI Provider)
```

## Personal Mode 关键决策

### 1. 向量检索为什么默认不用 FAISS/Milvus?

个人相册量级、512 维 float32，NumPy 暴力检索通常足够；接口隔离在
`VectorIndex` / `vectorstore.py`，后续可替换。

### 2. 三路混合检索怎么融合?

语义、OCR、结构化硬过滤，再按意图动态调整 RRF 权重。

### 3. 断点续建

调度依据 `index_jobs`，失败指数退避，心跳超时回收；结果与任务状态同事务提交。

### 4. 模型降级

`onnx → transformers → demo`；OCR/人脸缺失记 `skipped`，不冒充成功。

## Enterprise Mode 关键决策

### 1. 为什么业务库切到 PostgreSQL?

需要多租户 RLS、HNSW、任务状态机、审计和独立迁移权限边界。
SQLite 仍保留给 Personal Mode。

### 2. Worker 为什么独立?

API 进程不加载模型；Celery Worker 负责缩略图/向量/OCR/人脸。
未实现的 Processor（如 `face_cluster`、`vector_sync`）会显式失败，
禁止“无结果却 succeeded”。

### 3. 租约 fencing

任务 claim 绑定 `worker_id`；完成、跳过、失败写入都必须匹配当前租约，
避免旧 Worker 覆盖新 Worker 结果。

### 4. OCR

当前为企业基础版：`simple` tsvector + `ILIKE` + `pg_trgm` GIN。
个人模式的中文 n-gram 尚未完全等价迁移到企业检索特征。

### 5. 人脸

企业模式已保存人脸向量和 `person_key` 字段预留；
人物聚类、命名、合并拆分、按人物召回仍未完成。

## 数据流（一次企业搜索）

```text
query
  → parse_rules
  → semantic candidates (pgvector)
  → OCR candidates (tsvector / ILIKE / trigram index)
  → metadata filters + collection ACL
  → ExplainableReranker
  → matched_by / feature contributions
```
